The PR Hub · Data Model for 8 Edges Company OS · v0.5 draft

Client Activity Record — Database Framework

The PR-specific data model to build into the existing 8 Edges Company OS — hanging off the Company that's already there, living under a PR Program, and using the platform's Internal / Client Hub switch for visibility. Field names are suggestions; the shape, the relationships, and what plugs into what are the point.

Anchors onto: Company → PR Program Visibility: the Internal / Client Hub toggle Golden rule: no credentials stored, ever

How this plugs into Company OS

You already have the right containers — Company, Contacts, PR Programs, and the Internal / Client Hub toggle. We don't rebuild those; the PR activity model attaches to them. The current placeholder tabs (Work Board, Roadmap, Documents, Meetings, Invoices) are not what we're modelling to.

◇ Reuse what's already there

Platform primitives — don't rebuild

  • company — the client org (EM Advisory). Everything keys back to it.
  • pr_program — the engagement ("PR Retainer"). The PR account home lives here.
  • contact — the client's people, already a platform entity.
  • Internal / Client Hub — the built-in visibility switch = our client-facing flag.
+ Build the PR domain

New tables the developer adds

  • quarterly_plan · plan_target — the agreed 90-day plan
  • workstream · activity — the categories and the daily log
  • media_coverage · linkedin_post · award — earned outcomes + tallies
  • linkedin_strategy · news_pipeline · media_contact · touchpoint

The key alignment: there is no separate “client” table. One PR Program per client account is the anchor — it belongs to a Company, and every PR table below hangs off program_id. That means client #2 is a new Program on its Company, not a rebuild.

⚠ Security — non-negotiable

The old Key Facts sheet stores LinkedIn login passwords in plain text. The database must never hold a password. We keep the linkedin_handle and login email so the team knows which account, but the credential itself lives in a password manager (1Password) — the record holds at most a credential_ref pointer, never the secret. Same rule for any client login.

The spine: Plan → Effort → Outcome

Almost everything the team does has three layers. Naming them keeps the record honest — you can always ask “did what we agreed turn into work, and did that work turn into results?”

1 · Plan

What the client agreed

The 90-day business + communication objectives (the drift yardstick), the plan and its targets, awards proposed, LinkedIn strategy. quarterly_plan, plan_target

2 · Effort

What the team is doing

The daily log of individual activities under each workstream. This is the account team's scorecard. activity

3 · Outcome

What we got

The earned results, kept forever — coverage, posts, awards won. These feed the live home-page tallies. media_coverage, linkedin_post, award

+ the why

When plan ≠ did — something agreed didn't happen in the timeframe — the record captures a reason (a dropdown) and a note, so the story is always “the deal took longer than the client expected”, never a silent gap that reads as a missed delivery.

Seven decisions baked into this shape

The choices that stop this becoming another sheet that rots.

01 / ANCHOR

One PR Program per client, not a new “client” table

The account home lives on pr_program, which belongs to the existing company. Every PR table keys to program_id. Adding client #2 is a new Program on its Company — copy-paste, not a rebuild.

02 / THE SPINE

Plan, Effort and Outcome are separate layers

Kept apart, they answer the question you care about: is agreed work turning into activity, and activity into results? Mixing them into one “status” cell is what made the old sheets unreadable.

03 / PATTERN

“Proposed vs actual” is one table, not two

Awards use one stage field (proposed → agreed → submitted → outcome) — the two on-screen lists are filtered views. LinkedIn splits into a strategy (plan) and post (record).

04 / AUTOMATION

Everything countable is calculated live

Home-page tallies for LinkedIn posts and media coverage are COUNT() rollups — real-time, never typed. The same engine builds the account team's EOS scorecard from the activity log. No monthly admin.

05 / VISIBILITY

Uses the Internal / Client Hub toggle you already have

Rows and tables map to your built-in switch. Client Hub shows: plan, coverage, LinkedIn, their Drive folder. Internal only: account health, the media contacts database, newsjacking, internal Drive, owners and notes.

06 / THE UPDATE LOOP

One append-only log the team touches daily

activity is where each item is logged under its workstream — a news announcement, a reactive pitch, a newsjack, speaking photos. Adding rows (by hand or by AI from a transcript) is the habit that survives.

07 / THE WHY

Every gap has a reason, and it's never “we didn't deliver”

variance_reason (a dropdown) plus a note record why something slipped — client delayed, deal not finalised, reprioritised. The status vocabulary is client-friendly, so the Client Hub always reads a clean state with an honest explanation.

Notes for the developer

  • Anchor everything to the existing Company. No new “client” entity — a pr_program row per client account, company_id FK. All PR tables key to program_id.
  • Reuse the Internal / Client Hub toggle for visibility. The Client Hub role sees only Client-Hub tables and rows where in_client_hub = true. Never expose media_contact, touchpoint, account_health, or internal_drive_folder to a client.
  • Tallies and the EOS scorecard are views, not columns. coverage_count, linkedin_post_count, and account-team metrics are computed queries/materialised views — nobody edits a number.
  • File uploads (TV/radio segments) go to object storage; the DB stores the URL, not the file.
  • No credentials, ever. Client access is via the platform login; passwords live in a password manager.
  • Open question, not blocking: media contacts are per-program as requested — if a journalist covers several clients this could later become shared. Flagging, not deciding.
